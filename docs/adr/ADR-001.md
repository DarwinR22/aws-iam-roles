# ADR-001: Enterprise ABAC Architecture for IAM Management

**Status:** Accepted  
**Date:** 2024-01-15  
**Decision Makers:** Security Team, DevOps Team, Architecture Council  
**Consulted:** Development Teams, Platform Teams  
**Informed:** All Engineering Teams  

## Context

Claro CENAM's IAM management has evolved from a simple role-based system to requiring enterprise-grade attribute-based access control (ABAC) with strict governance, compliance, and security requirements.

### Current Challenges
- Manual IAM role creation leading to inconsistencies
- Lack of standardized permission boundaries
- Insufficient tag governance for SOX compliance
- Security policy validation gaps
- No centralized catalog for IAM resources
- Drift detection not automated

### Requirements
- **Compliance**: SOX, internal audit requirements
- **Security**: Zero-trust principles, least privilege
- **Governance**: Automated guardrails, policy validation
- **Operations**: Infrastructure as Code, automated CI/CD
- **Standardization**: Canonical tags, naming conventions

## Decision

We will implement an **Enterprise ABAC Architecture** with the following components:

### 1. Core Architecture Principles

#### Attribute-Based Access Control (ABAC)
- **Tag-based permissions**: Resources grant access based on matching principal tags with resource tags
- **Conditional access**: All policies include conditions comparing `aws:PrincipalTag` with `aws:ResourceTag`
- **Service-specific tags**: S3 uses `s3:ExistingObjectTag`, Lambda uses `lambda:FunctionTag`

#### Permission Boundaries
- **App-StandardBoundary**: For application roles, denies dangerous IAM/Organizations actions
- **Platform-Boundary**: For infrastructure roles, allows more permissions but restricts critical actions
- **Mandatory**: All roles must have a permission boundary attached

#### Canonical Tags (23 Required)
```yaml
Ambiente, País, Dirección, Gerencia, Cuenta, Módulo, Alcance SOX, 
Propietario, Proveedor, Layer, Dominio, Subdominio, Aplicación, Name, 
Soporte, Contacto, Proyecto, Fechas de Creación, Creado Por, 
Tipo de Recurso, Ciclo de Vida, Versión, Map-migrated
```

### 2. Technical Components

#### Repository Structure
```
mci-aws-iam/
├── modules/                    # Terraform modules
│   ├── iam-role/              # Role creation with ABAC validation
│   ├── iam-managed-policy/    # Policy creation with validation
│   └── iam-attachments/       # Policy attachment management
├── policy_lib/                # Reusable policy building blocks
│   ├── s3/                    # S3 ABAC policies
│   ├── dynamodb/              # DynamoDB ABAC policies
│   ├── lambda/                # Lambda ABAC policies
│   ├── sqs/                   # SQS ABAC policies
│   └── commons/               # Trust policies, boundaries
├── catalog/                   # Single source of truth
│   ├── roles.yaml             # Role definitions
│   └── policies.yaml          # Policy definitions
├── guardrails/                # Security validation
│   ├── conftest/              # OPA/Rego rules
│   └── checkov/               # Security scanning
├── ci/                        # CI/CD pipelines
│   ├── terraform.yml          # Validation & planning
│   ├── apply.yml              # Deployment
│   └── drift-detection.yml    # Daily drift monitoring
└── docs/                      # Documentation
```

#### Policy Building Blocks
- **S3**: Tag-based read/write with prefix conditions
- **DynamoDB**: Tag-based access with LeadingKeys support
- **Lambda**: Tag-based invoke with execution permissions
- **SQS**: Tag-based produce/consume patterns
- **Commons**: Secure service trusts, permission boundaries

#### Validation Pipeline
1. **fmt** → **validate** → **tflint** (Code quality)
2. **conftest** → **checkov** → **access-analyzer** (Security)
3. **plan** → **artifact** → **manual-apply** (Deployment)

### 3. Security Guardrails

#### OPA/Conftest Rules
- Deny `Action: "*"` without conditions
- Require permission boundaries on all roles
- Validate canonical tags presence and format
- Require `aws:SourceAccount` in service trusts
- Require `s3:prefix` for ListBucket actions

#### Checkov Custom Checks
- ABAC condition validation in TagBased policies
- Permission boundary enforcement
- Canonical tags compliance

#### AWS Access Analyzer
- Policy syntax validation
- Security findings detection
- Policy simulation

### 4. Operational Model

#### Source of Truth
- **catalog/roles.yaml**: All role definitions
- **catalog/policies.yaml**: All policy definitions
- **Terraform**: Infrastructure as Code implementation
- **Git**: Version control and change tracking

#### Deployment Process
1. Update catalog YAML files
2. CI pipeline validates changes
3. Security team reviews policy_lib changes
4. Manual approval for production
5. Automated deployment with verification

#### Monitoring & Compliance
- **Daily drift detection**: Automated configuration drift alerts
- **Security reviews**: Required for policy_lib changes
- **Audit trails**: All changes tracked in Git history
- **Compliance reporting**: Tag compliance, boundary coverage

## Consequences

### Positive
- **Enhanced Security**: ABAC provides fine-grained access control
- **Compliance**: Automated validation ensures SOX compliance
- **Consistency**: Standardized approach across all environments
- **Auditability**: Complete audit trail and automated compliance checks
- **Scalability**: Reusable policy blocks reduce management overhead
- **Reliability**: Automated testing prevents misconfigurations

### Negative
- **Complexity**: Learning curve for teams unfamiliar with ABAC
- **Migration Effort**: Existing roles need conversion to new architecture
- **Dependency**: Teams must follow canonical tag requirements
- **Performance**: Additional validation steps in CI/CD pipeline

### Risk Mitigation
- **Training**: Comprehensive documentation and examples provided
- **Gradual Migration**: Phased approach with backward compatibility
- **Tooling**: Automation reduces manual errors and complexity
- **Support**: Security team provides guidance during transition
